# MISSION.md 格式规范

`MISSION.md` 保存在工作区根目录。它捕获了用户学习该主题的*原因*。每一个教学决策 — 接下来教什么、呈现哪些资源、设计哪些练习 — 都应该追溯到这份文档。

## 模板

```md
# 使命：{Topic}

## 为什么 (Why)
{1-3 句话。用户追求的具体现实世界目标。当他们掌握这项 Skill 时，他们的生活或工作发生了什么变化？避免使用“为了理解 X”这样的抽象表述 — 推动追求底层的实际结果。}

## 成功的标志 (Success looks like)
- {用户将能够做到的具体、可观察的事项}
- {另一件具体事项}
- {…}

## 约束条件 (Constraints)
- {时间、预算、先前的承诺、学习偏好、任何界定方法边界的事项}

## 超出范围 (Out of Scope)
- {用户明确不想在当前追求的相邻主题 — 保护最近发展区}
```

## 规则

- **每个工作区一个使命。** 如果用户想要学习两个无关的事项，那是两个独立的工作区。
- **具体胜于抽象。** “在 10 月前跑完半程马拉松”胜过“变得更健康”。“向我的团队发布一个 Rust CLI”胜过“学习 Rust”。
- **推翻模糊表述。** 如果用户无法清晰表达原因，在编写任何内容之前先访谈他们。糟糕的使命比没有使命更糟。
- **当现实发生转变时进行修订。** 使命会变。当用户的目标移动时，更新此文件 — 不要留下一份过时的使命指导未来的环节。
- **保持简短。** 如果 `MISSION.md` 超过了一屏，它就从指南针变成了详细计划。
