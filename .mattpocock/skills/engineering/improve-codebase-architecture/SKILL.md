# 改善代码库架构 (Improve Codebase Architecture)

浮现架构摩擦并提出**模块深化机会 (deepening opportunities)**——将浅层模块转化为深层模块的重构方案。其目标是提升可测试性与 AI 可导航性。

本命令受项目的领域模型**启发指导**，并构建在共享的设计词汇表之上：

- 运行 `/codebase-design` 技能获取架构词汇表（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆力**、**局部性**）及其设计原则（删除测试法、“接口即测试表面”、“单个适配器 = 假想接缝，两个 = 真实接缝”）。在每一条建议中都必须精确使用这些术语——不要偏离为“组件 (component)”、“服务 (service)”、“API”或“边界 (boundary)”。
- `CONTEXT.md` 中的领域语言为良好的接缝命名；`docs/adr/` 中的 ADR 记录了本命令不应重新争论的决策。

## 流程

### 1. 探索 (Explore)

**在扫描前确定范围 — YAGNI (你不需要它)。** 深化一个模块的回报在于使其未来的变更更加容易，因此要将额外的权重放在代码库最近发生变更的部分。在看之前先决定去*哪里*看：

- 如果用户给出了明确的方向——某个模块、子系统、痛点——遵循该方向，并跳过下文的推断。
- 否则，拉取较长一段 commit 历史（`git log --oneline`）以查找代码库的热点区域——那些反复出现变更的文件和区域——让这些路径优先吸引你的注意力。如果变更很零散且没有明显的热点，再扩大搜索网。

首先阅读项目的领域词汇表 (`CONTEXT.md`) 以及你触及领域的任何 ADR。

然后使用 Agent 工具并指定 `subagent_type=Explore` 来浏览代码库。不要遵循僵硬的启发式规则 — 自然地探索，并记录你在哪里感受到了摩擦：

- 在哪里理解一个概念需要跨许多小模块来回反复跳跃？
- 在哪里模块是**浅层 (shallow)** 的 — 接口几乎与实现一样复杂？
- 在哪里仅仅为了可测试性而提取了纯函数，但真正的 Bug 却隐藏在它们被调用的方式中（缺乏**局部性 locality**）？
- 在哪里紧密耦合的模块跨越其接缝发生泄漏？
- 代码库的哪些部分未经测试，或者难以通过其当前的接口进行测试？

对你怀疑是浅层的任何事物应用**删除测试法 (deletion test)**：删除它会使复杂性集中，还是仅仅移动了复杂性？“是的，会集中”就是你想要的信号。

### 2. 将候选方案展示为 HTML 报告 (Present candidates as an HTML report)

将一个自包含的 HTML 文件写入 OS 临时目录，以确保不会有任何临时文件落入仓库中。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（或 Windows 上的 `%TEMP%`），并写入到 `<tmpdir>/architecture-review-<timestamp>.html`，使每次运行都能获得一个新鲜的文件。为用户打开该文件 — Linux 上为 `xdg-open <path>`，macOS 上为 `open <path>`，Windows 上为 `start <path>` — 并告诉他们绝对路径。

报告使用 **CDN Tailwind** 进行布局和样式设计，并在图表（图/流/时序图）能够稳定可靠传达结构时使用 **CDN Mermaid**。将 Mermaid 与手绘 CSS/SVG 视觉效果结合起来 — 当关系呈图状（调用图、依赖关系、时序）时使用 Mermaid，当你想要更具编辑感的内容（块体图、截面图、折叠动画）时使用手工构建的 div/SVG。每个候选方案都配有**重构前/后对比可视化图**。要注重视觉呈现。

对于每个候选方案，渲染一张包含以下内容的卡片：

- **相关文件 (Files)** — 涉及哪些文件/模块
- **痛点 (Problem)** — 为什么当前的架构正在引发摩擦
- **解决方案 (Solution)** — 用通俗平实的语言描述改变了什么
- **收益 (Benefits)** — 用局部性和杠杆力阐述收益，以及测试将如何改善
- **重构前/后对比图 (Before / After diagram)** — 两列并排、自定义绘制，插图说明浅薄性与深化重构
- **推荐强度 (Recommendation strength)** — `Strong`（强力推荐）、`Worth exploring`（值得探索）、`Speculative`（推测性）之一，渲染为徽章

报告以**顶级推荐 (Top recommendation)** 章节结尾：你会优先处理哪个候选方案以及原因。

**在领域方面使用 CONTEXT.md 词汇，在架构方面使用 `/codebase-design` 词汇。** 如果 `CONTEXT.md` 定义了“Order (订单)”，在谈论时使用“the Order intake module (订单接收模块)” — 而不是“the FooBarHandler”，也不是“the Order service”。

**ADR 冲突处理**：如果某个候选方案与现有的 ADR 冲突，仅在摩擦足够真实且值得重新评估该 ADR 时才浮现出来。在卡片中清晰标记（例如警告提示框：*"与 ADR-0007 冲突 — 但值得重新讨论，因为…"*）。不要列出 ADR 所禁止的每一个理论上的重构方案。

有关完整的 HTML 骨架、图表模式和样式指南，请参见 [HTML-REPORT.md](HTML-REPORT.md)。

切勿在此阶段直接提出接口方案。文件写入完成后，询问用户：“你希望探究其中的哪一个？”

### 3. 追问探究循环 (Grilling loop)

一旦用户挑选了一个候选方案，运行 `/grilling` 技能与其一起梳理决策树 — 约束条件、依赖关系、深化模块的形状、接缝背后的内容、留存下来的测试。

随着决策的定型，副作用在线发生 — 运行 `/domain-modeling` 技能随之保持领域模型的最新状态：

- **使用不在 `CONTEXT.md` 中的概念命名深化后的模块？** 将该术语添加到 `CONTEXT.md` 中。如果文件不存在，延迟创建它。
- **在对话期间锤炼了模糊的术语？** 当场更新 `CONTEXT.md`。
- **用户以承重性的理由拒绝了候选方案？** 主动提供 ADR，表述为：*"需要我将其记录为 ADR 吗，这样未来的架构审查就不会再次建议它了？"* 仅在未来探究者确实需要该理由以避免再次提出相同建议时才提供 — 跳过临时性理由（“现在不值得做”）和显而易见的理由。
- **希望探索深化模块的替代接口方案？** 运行 `/codebase-design` 技能并使用其“两次设计”并行子代理模式。
