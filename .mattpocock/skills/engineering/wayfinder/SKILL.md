# 寻路（Wayfinder）

一个模糊的想法已经传来 — 对于单个 Agent 会话来说过于庞大，且裹挟在迷雾中：从这里通往**终点（destination）**的路径尚未清晰可见。寻路关乎于找到这条路径，而不是径直向终点冲锋。本 Skill 在仓库的 issue 追踪器上将路径绘制为一张**共享地图（shared map）**，然后处理其**决策工单（decision tickets）** — 这些工单的问题其解法是决议而非待执行的构建切片 — 逐一解决它们，直到路线变得清晰。

每个工作项的终点各有不同，而对其命名是绘制地图的首要行为 — 它塑造了每张工单。它可能是一份待移交并迭代的规范 spec、一个在规划开始前锁定的决议，或者像数据结构迁移那样在原位做出的变更。地图是与具体领域无关的 — 工程工作、课程内容，只要符合其形状即可。

## 规划，而非实施

Wayfinder 默认是**规划（planning）**：每张工单解决一个决议，当路径清晰时地图即告完成 — 在有人去动手实施之前没有任何需要决定的内容残留。直接去动手做工作的冲动通常是一个信号，表明你已经到达了地图的边缘，该交接了。某项工作可以在其**笔记（Notes）**中覆盖这一点 — 将执行引入地图本身 — 但若无此说明，请产出决议，而非交付物。

## 按名称引用

每张地图和工单都是一个 issue，因此它都有一个**名称（name）** — 即其标题。在人类阅读的所有内容中 — 旁白、地图的“迄今为止的决议” — 请按名称来引用它，绝不要使用裸 ID、编号或 slug。满屏的 `#42, #43, #44` 是不可读的；名称可以一目了然。ID 和 URL 不会消失 — 名称包裹着其链接 — 但它们包含在名称*内部*，绝不替代名称本身。

## 地图（The Map）

地图是此仓库 issue 追踪器上的单个 issue，标记有 `wayfinder:map` — 规范的产物。其工单是地图的子 issue。

地图是一个**索引（index）**，而非存储库。它列出了做出的决议并指向保存其细节的工单；决议恰好存在于一个地方 — 其工单 — 因此地图从不重述它，只做摘要和链接。

**地图、其子工单、阻塞和前沿查询在物理上保存在哪里是特定于追踪器的。** 应该已向你提供了 issue 追踪器 — 如果没有，请运行 `/setup-matt-pocock-skills`。请参阅追踪器文档的“寻路（Wayfinding）操作”章节，了解*本*仓库如何表达它们。如果未提供追踪器，默认使用本地 markdown 追踪器。

### 地图正文

整个地图的低分辨率视图，每个会话加载一次。开启状态的工单**不**在此列出 — 它们是未关闭的子 issue，通过查询获取。

```markdown
## Destination

<到达此地图终点时的样子 — 本次努力寻找路径所通向的 spec、决议或变更。一到两行；每个会话在选择工单之前先在此进行定向。>

## Notes

<领域；每个会话应查阅的 skill；本次努力的立足偏好>

## Decisions so far

<!-- 索引 — 每个已关闭工单一行：足以判断相关性，然后放大链接以查看工单持有的细节 -->

- [<已关闭工单标题>](link) — <答案的一句话摘要>

## Not yet specified

<!-- 参见 "战争迷雾"：你尚无法开出工单的范围之内的迷雾；随着前沿的推进而毕业 -->

## Out of scope

<!-- 参见 "范围之外"：判定超出终点的工作；已关闭，绝不毕业 -->
```

### 工单（Tickets）

每张工单都是地图的一个**子 issue**；追踪器的 issue id 是其身份标识。其正文是问题本身，尺寸设计为容纳在一个 100K token 的 Agent 会话中：

```markdown
## Question

<本工单解决的决议或调查>
```

每张工单携带一个 `wayfinder:<type>` 标签 — `research`、`prototype`、`grilling`、`task` 之一（参见 [工单类型](#工单类型)）。

会话在开展任何工作之前，**首先**通过将工单分配给驱动地图的开发者来**申领（claim）**它，以便并发会话跳过它。该被分配者*就是*申领标志：一个未关闭且未分配的工单就是未申领的。

阻塞使用追踪器的**原生**依赖关系 — 这至关重要，因为它在追踪器自身的 UI 中*直观地*渲染前沿，因此人类无需打开地图即可看到什么是可领取的。只有缺乏原生阻塞的追踪器才会回退到正文约定。当阻塞某工单的所有工单都已关闭时，该工单被**解除阻塞**；**前沿（frontier）**就是开启、未阻塞且未申领的子项 — 已知领域的边缘。

答案不是正文的一部分 — 它在解决时记录（参见 [贯穿地图开展工作](#贯穿地图开展工作)）。在解决工单期间创建的资产从 issue 处链接，而不是直接粘贴进来。

## 工单类型（Ticket Types）

每张工单要么是 **HITL**（Human in the loop，人机协同） — 与能代表自己说话的人类*共同*开展；要么是 **AFK**（离线） — 由 Agent 独立驱动。HITL 工单仅通过现场交流来解决；Agent 切勿代替人类出面（自己回答自己问题的追问 Agent 就打破了这一点）。

- **Research** (AFK)：阅读文档、第三方 API 或知识库等本地资源，以展现决议所等待的事实。由 `/research` **子代理**解决。当需要当前工作目录之外的知识时使用。
- **Prototype** (HITL)：通过制作轻便、粗糙、具体的产物来做出回应，从而提高讨论的保真度 — 概要、粗略方案、存根，或通过 `/prototype` Skill 制作 UI/逻辑代码。将原型作为资产进行链接。当“应该长成什么样”或“应该如何表现”是核心问题时使用。
- **Grilling** (HITL)：通过 `/grilling` 和 `/domain-modeling` Skill 进行对话，一次一个问题。默认情况。
- **Task** (HITL 或 AFK)：在做出*决议*之前必须发生的动手工作 — 没有需要决定的、原型的或研究的内容，但讨论被阻塞直至其完成。注册某项服务以便评估其 API、配置权限、移动数据以便查看其形状。这是*做*而非*决定*的一种类型 — 它通过解除决议的阻塞来赢得其地位，而不是通过交付终点来赢得地位。Agent 在可行的情况下独立驱动它 (AFK)；否则它给人类递上一份精确的检查清单 (HITL)。工作完成时解决；答案记录做过的动作以及后续工单所依赖的任何衍生事实（凭据位置、新 URL、行数）。

## 战争迷雾（Fog of war）

地图是*故意*不完整的：不要绘制你还看不到的内容。在实时工单之外矗立着**战争迷雾（fog of war）** — 对你能够预见即将到来但尚无法钉死的决议和调查的模糊视角，因为它们悬停在尚未解决的问题之上。解决一张工单会扫清其前面的迷雾，将现在可以规范化的内容毕业为新的工单 — 一次一个，直到通往终点的路径清晰且不再残留工单。

地图的 **Not yet specified**（尚待规范）章节是记录这种模糊视角的地方：怀疑的问题、稍后重新访问的区域。它是通往终点的未探索前沿 — 这里的所有内容都在范围之内，只是还不够清晰以开出工单。尽可能松散或尽可能充分地撰写视角所允许的内容；它兼作阅读工作走向的协作者的路标。

**迷雾还是工单？** 检验标准是你现在是否能够精准陈述问题 — *而不是*你现在能否回答它。

- **开出工单：当**问题已经非常清晰 — 即使它被阻塞且你现在尚无法对其采取行动。
- **尚待规范：当**你还不能将其描述得足够清晰时。不要将迷雾预先切成工单大小的碎块：它比工单更粗糙，一旦前沿触及它，一个快照可能会毕业成几张工单，或者一张都没有。

**Not yet specified** 排除已经决定的内容（Decisions so far）、已经是实时工单的内容，以及超出范围的内容（下一章节）。

## 范围之外（Out of scope）

迷雾只会在*通往*终点的方向聚集。终点确定了范围，因此超出终点的工作是**超出范围（out of scope）** — 它不是迷雾，也不属于 **Not yet specified**。它在地图上拥有自己的 **Out of scope** 章节：你自觉排除在*本次*工作之外的工作。是范围，而不是清晰度，决定了它停留在该章节。

范围之外的工作绝不会毕业 — 前沿止于终点 — 因此它只有在终点重新绘制时才会返回，并且届时作为一项全新的努力返回，而不是恢复原状。

将某项内容判定为超出范围是一项范围界定行为，而不是路线上的一个步骤。当一张已经存在的工单结果位于终点之外时 — 在绘制时错误划入，或者因某项解决而暴露出来 — **关闭它**（关闭的工单明确地从前沿移除），并在 **Out of scope** 章节留下行：摘要加上超出范围的原因，并链接被关闭的工单。它不会进入 **Decisions so far**，后者记录的是实际走过的路线 — 范围边界并不是路线上的步骤。

## 调用

两种模式。无论哪种方式，**单个会话中决不要解决多于一张的工单** — 但 research 工单除外。

### 绘制地图（Chart the map）

用户凭借模糊的想法调用。

1. **命名终点。** 运行 `/grilling` 和 `/domain-modeling` 会话，以钉死本地图正在通往的终点 — spec、决议或变更。终点确定了范围，因此首先得到解决。
2. **绘制前沿地图。** 再次追问，这次采用**广度优先**：横跨整个空间展开，而不是深入任何单个线程，显化开放的决议和现在可以采取的第一步。**如果这没有暴露任何迷雾** — 通往终点的路径已经清晰，整个旅程小到足以在一个会话中容纳 — 你不需要地图。停下来并询问用户希望如何推进。
3. **创建地图** (标签 `wayfinder:map`)：填好 Destination 和 Notes，Decisions-so-far 留空，将迷雾勾勒进 **Not yet specified**。
4. **在第二轮中创建你现在可以规范化的工单** 作为地图的子 issue — 然后在**第二轮**中连接阻塞边（issue 在彼此引用前需要 ID）。连接将它们排序入前沿和被阻塞项中；你尚无法规范化的所有内容都留在迷雾中 — **Not yet specified** 章节。
5. **触发 research 子代理。** 对于你刚创建的每张 `research` 工单，启动一个 `/research` 子代理并行解决它，在抛弃型 `research/<name>` 分支上捕获其结果，并附带来自工单的上下文指针。
6. 停止 — 绘制地图是一个会话的工作；它不手动解决任何问题。

### 贯穿地图开展工作（Work through the map）

用户使用地图（URL 或编号）调用。工单是**可选的** — 没有指定工单时，由你选择下一个决议，而不是用户。

1. 加载**地图** — 低分辨率视图，而不是每张工单的正文。
2. 选择工单。如果用户指定了一张，使用它。否则按照顺序取第一张前沿工单。**申领它**：在进行任何工作之前将其分配给自己。
3. 解决它 — **根据需要放大**：按需获取任何相关或已关闭工单的完整正文；调用 `## Notes` 块命名的 Skill。如有疑问，使用 `/grilling` 和 `/domain-modeling`。
4. 记录决议：将答案作为**决议评论（resolution comment）**发表，**关闭** issue，并在地图的 Decisions-so-far 中**追加一个上下文指针**。
5. 添加最新显化的工单（先创建后连接）；将答案已使其变得可规范化的任何迷雾毕业，从 **Not yet specified** 中清除每个毕业的快照，以便它仅作为其新工单存在。如果答案揭示了一张工单 — 本工单或另一张 — 位于终点之外，**将其判定为超出范围**，而不是在路线上解决它。如果决议使地图的其他部分失效，更新或删除这些工单。

用户可能会并行运行未阻塞的工单，因此请预期其他会话正在并发编辑追踪器。
