# 分类（Triage）

驱动项目 issue 追踪器上的 issue 经过由分类角色组成的小型状态机。

如果此仓库将外部 pull request 视为请求入口（参见 issue-tracker 配置），分类同样覆盖它们：**PR 是带有附加代码的 issue** — 相同的角色、相同的状态、相同的状态机，仅有少数在下方标记为“对于 PR”的增量区别。根据追踪器配置将单独的 `#42` 解析为 issue 或 PR。

在分类期间发表到 issue 追踪器的每一条评论或 issue 都**必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何编写耐久的 Agent brief

## 角色

两个**类别（category）**角色：

- `bug` — 某项内容被破坏
- `enhancement` — 新功能或改进

五个**状态（state）**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 已完整规范化，准备好交给离线 Agent
- `ready-for-human` — 需要人工来进行实现
- `wontfix` — 不会采取行动

对于 PR，相同的状态对照附加的代码进行解读：`ready-for-agent` 意味着已附上 brief 且 Agent 应该对 diff 采取下一步行动；`ready-for-human` 意味着已准备好供人工进行合并。

每个经过分类的 issue 都应该恰好携带一个类别角色和一个状态角色。如果状态角色发生冲突，在采取任何行动之前请标记出来并询问维护者。

这些是规范的角色名称 — issue 追踪器中实际使用的标签字符串可能有所不同。映射关系应该已提供给你 - 如果没有，请运行 `/setup-matt-pocock-skills`。

状态迁移：未打标签的 issue 通常首先进入 `needs-triage`；从那里移动到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦报告者做出回复，`needs-info` 重新回到 `needs-triage`。维护者可以随时覆盖 — 标记看起来异常的迁移并在推进前进行询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们的需求。解释请求并采取行动。示例：

- "Show me anything that needs my attention" (向我展示需要我关注的所有内容)
- "Let's look at #42" (让我们看看 #42，issue 或 PR)
- "Move #42 to ready-for-agent" (将 #42 移动到 ready-for-agent)
- "What's ready for agents to pick up?" (有哪些已准备好供 Agent 领取？)

## 展示需要关注的内容

查询 issue 追踪器并展示三个桶（bucket），最旧的在前：

1. **未打标签（Unlabeled）** — 从未分类。
2. **`needs-triage`** — 评估正在进行中。
3. **自上次分类笔记以来有报告者活动的 `needs-info`** — 需要重新评估。

当 PR 在作用域内时，在这些桶中包含外部 PR，并在每行标上 `[PR]` 或 `[issue]`。发现入口仅包含*外部* PR（追踪器配置定义了谁算作外部人员）— 合作者的进行中 PR 不属于分类工作。该过滤器仅用于发现；明确指定的 PR 无论作者是谁都会被分类。

展示计数以及每项的一句话摘要。让维护者进行挑选。

## 分类特定的 issue 或 PR

1. **收集上下文（Gather context）。** 阅读完整的 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还包括 diff）。解析先前的任何分类笔记，以免重复询问已解决的问题。使用项目的领域词汇表探索代码库，尊重该区域内的 ADR。针对代码库运行两项检查：(a) **冗余度（redundancy）** — 通过领域概念（而不仅是请求的字面措辞）搜索请求行为的现有实现，并报告你查看的位置。如果找到，它属于已实现的 `wontfix`（步骤 5）。(b) **先前的拒绝（prior rejection）** — 阅读 `.out-of-scope/*.md` 并暴露任何类似于此请求的内容。

2. **推荐（Recommend）。** 向维护者提供你的类别和状态推荐及推导理由，外加与请求相关的简要代码库摘要 — 包括它是否已被实现。等待指示。

3. **验证主张（Verify the claim）。** 在任何追问（grilling）之前，检查主张是否站得住脚。对于 bug，从报告者的步骤复现它。对于 PR，确认 diff 是否实现了其声明的功能 — 检出代码，运行相关的测试或命令。报告发生的情况：确认（附带代码路径）、失败或细节不足（强烈的 `needs-info` 信号）。经确认的验证能打造强得多的 Agent brief。

4. **深入追问（Grill，如果需要）。** 如果请求需要具体充实，同时运行 `/grilling` 和 `/domain-modeling` Skill — 一次一个问题地将其追问成型，随着决议落地，原地磨炼领域术语并更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发表一条 Agent brief 评论 ([AGENT-BRIEF.md](AGENT-BRIEF.md))。
   - `ready-for-human` — 与 Agent brief 结构相同，但说明为何无法委托给 Agent（价值判断、外部权限、设计决议、手动测试）。
   - `needs-info` — 发表分类笔记（模板见下方）。
   - `wontfix` — 关闭，评论取决于*原因*：
     - **已经实现** — 变更已存在于代码库中。指明其所在位置；**不要**写入 `.out-of-scope/`（该知识库适用于被*拒绝*的请求，而非已构建的请求）。
     - **拒绝 (bug)** — 礼貌解释，然后关闭。
     - **拒绝 (enhancement)** — 写入 `.out-of-scope/`，从评论中链接到它，然后关闭 ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   - `needs-triage` — 应用该角色。如果有阶段性进展可附带可选评论。

## 快速状态覆盖

如果维护者说 "move #42 to ready-for-agent"，信任他们并直接应用该角色。确认你即将进行的操作（角色变更、评论、关闭），然后采取行动。跳过追问。如果在没有追问会话的情况下移动到 `ready-for-agent`，询问他们是否希望编写 Agent brief。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

在 "established so far" 下捕获追问期间解决的所有内容，以免工作丢失。问题必须具体且具可操作性，而不是 "please provide more info"。

## 恢复之前的会话

如果 issue 或 PR 上存在先前的分类笔记，阅读它们，检查报告者是否回答了任何未决问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
