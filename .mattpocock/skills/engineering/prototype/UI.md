# UI 原型（UI Prototype）

在单一路由上生成**若干个截然不同的 UI 变体**，可通过底部悬浮栏进行切换。用户在浏览器中切换变体，挑选一个（或从每个变体中吸收部分设计），然后抛弃其余变体。

如果问题是关于逻辑/状态而非外观展示——分支选择错误。请使用 [LOGIC.md](LOGIC.md)。

## 适用场景

- "这个页面应该长成什么样？"
- "在提交设计之前，我想查看该仪表板的几种备选方案。"
- "尝试为设置页面设计不同的布局。"
- 任何如果不上原型，用户就需要在脑海中花上一整天在三个模糊的高保真设计稿之间纠结的场景。

## 两种子形状 — 强烈推荐子形状 A

当 UI 原型**与应用的其余部分紧密接合**时（真实页眉、真实侧边栏、真实数据、真实密度），更容易对其进行评估。独立存在的抛弃型路由处于真空状态：孤立地看每个变体都很不错。只要存在合理的现有页面来承载变体，默认选择子形状 A。只有当原型确实没有临近的宿主时，才考虑子形状 B。

### 子形状 A — 对现有页面的调整（首选）

路由已存在。变体渲染**在同一个路由上**，由 `?variant=` URL 查询参数控制。现有的数据获取、参数和身份验证都保持不变 — 仅切换渲染视图。这是默认选项；除非有特定理由不这样做，否则请选择它。

如果原型针对的是尚无页面但*自然会置于某个页面内部*的内容（仪表板的新板块、设置屏幕上的新卡片、现有流程中的新步骤）— 这仍然属于子形状 A。将变体挂载在宿主页面内部。

### 子形状 B — 新页面（不得已的备选）

仅在被原型的对象确实没有可寄宿的现有页面时使用 — 例如全新的顶层界面，或者无法合理嵌入任何位置的流程。

按照项目已有的任何路由约定创建一个**抛弃型路由** — 不要发明新的顶层结构。给它命名使其明显是原型（例如在路径或文件名中包含 `prototype` 一词）。采用相同的 `?variant=` 模式。

在决定使用子形状 B 之前，请进行合理性检查：真的没有可以嵌入该内容的现有页面吗？一个空白路由会掩盖充实路由能暴露出来的设计问题。

在两种子形状中，底部悬浮栏都是完全相同的。

## 流程

### 1. 阐明问题并选择 N

默认选择 **3 个变体**。超过 5 个变体就不再是截然不同，而是变成了噪音 — 在此上限停住。

在原型的位置或文件顶部的注释中用一行字写下计划：

> "设置页面的三个变体，可通过 `?variant=` 切换，挂载在现有的 `/settings` 路由上。"

无论用户是否在线提出异议，这种做法都有效。

### 2. 生成截然不同的变体

草拟每个变体。要求每个变体满足：

- 页面的目标以及可访问的数据。
- 项目的组件库 / 样式系统（TailwindCSS, shadcn, MUI, 原生 CSS 等）。
- 清晰导出的组件名称，例如 `VariantA`, `VariantB`, `VariantC`。

变体必须在**结构上截然不同** — 不同的布局、不同的信息层级、不同的核心交互入口，而不仅仅是不同的颜色。三个微调的卡片网格不是 UI 原型，那是壁纸。如果两个草案过于相似，请根据“不得使用卡片网格”的明确指导重做其中一个。

### 3. 将它们连接在一起

在路由上创建一个切换器组件：

```tsx
// 伪代码 — 适配项目的框架
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于子形状 A（现有页面）：将所有现有数据获取逻辑保留在切换器之上；只有渲染的子树随变体改变。

对于子形状 B（新页面）：在 `/prototype/<name>` 下的抛弃型路由挂载相同的切换器。

### 4. 构建悬浮切换器

屏幕底部中央的小型固定位置栏，包含三个部分：

- **左箭头** — 切换到上一个变体（循环切换）。
- **变体标签** — 显示当前变体 Key，如果变体导出了名称，也显示该名称。例如 `B — 侧边栏布局`。
- **右箭头** — 切换到下一个变体（循环切换）。

行为：

- 点击箭头更新 URL 查询参数（使用框架的路由器 — Next 上使用 `router.replace`，React Router 上使用 `navigate` 等），以便变体可分享且在刷新后保持稳定。
- 键盘：`←` 和 `→` 方向键也可进行循环切换。当聚焦在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时，不要拦截方向键。
- 在视觉上与页面区分开（例如高对比度胶囊样式、微妙的阴影），以便一眼看出这不是被评估设计的一部分。
- 在生产构建中隐藏 — 基于 `process.env.NODE_ENV !== 'production'` 或等效检查进行门控，以防意外合并原型将切换栏发布给用户。

将切换器放在单个共享组件中，以便两种子形状都可以复用它。放置在项目共享 UI 所在的任何位置。

### 5. 移交使用

展示 URL（以及 `?variant=` 参数值）。用户在方便时会进行浏览切换。最有价值的反馈通常是 **“我想结合 B 的页眉和 C 的侧边栏”** — 那才是他们真正想要的设计。

### 6. 捕获答案并清理

一旦某个变体胜出，捕获答案 — 选择了哪个变体以及原因 — 然后按照 [SKILL](SKILL.md) 描述的方式捕获原型。将胜出者整合到真实代码中，并将其余部分移动到抛弃型分支，而不是合入 main：

- **Sub-shape A** — 将胜出者整合到现有页面中；从 main 中删除落选的变体和切换器。
- **Sub-shape B** — 将胜出变体提升为真实路由；从 main 中删除抛弃型路由和切换器。

整套变体是原始凭据，因此落脚在抛弃型分支上，而不是直接丢掉 — 残留在主分支中的变体组件和切换器很快会腐烂并给未来的阅读者带来困扰。

## 反模式

- **仅在颜色或文案上有差异的变体。** 那是微调，不是原型。真正的变体在结构上存在分歧。
- **在变体之间共享过多代码。** 共享 `<Header>` 是可以的；共享 `<Layout>` 则违背了初衷。每个变体都应该可以自由抛弃布局。
- **将变体连接到真实变更逻辑。** 只读原型就足够了。如果变体需要执行变更，请将其指向 Stub 桩函数 — 问题是“这应该长成什么样”，而不是“后端是否工作”。
- **直接将原型提升到生产环境。** 变体代码是在原型约束下编写的（无测试、最少的错误处理）。将其整合时请对其进行彻底重构。
