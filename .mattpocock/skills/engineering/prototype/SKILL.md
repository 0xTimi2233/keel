# 原型（Prototype）

原型是**用于回答问题的抛弃型代码**。问题决定了其形状。

## 选择分支

从用户的提示词、上下文代码中识别正在回答哪个问题，或者在用户在线时直接询问：

- **"该逻辑 / 状态模型感觉是否合适？"** → [LOGIC.md](LOGIC.md)。构建一个微型交互式终端应用，推动状态机推演在纸面上难以推理的用例。
- **"这应该长成什么样？"** → [UI.md](UI.md)。在单一路由上生成若干个截然不同的 UI 变体，可通过 URL 查询参数和底部悬浮栏进行切换。

这两个分支会生成截然不同的产物——选错分支会浪费整个原型。如果问题确实含糊不清且无法联系到用户，默认选择与周围代码更契合的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部说明假设。

## 适用于两者的通用规则

1. **从第一天起就是抛弃型代码，并明确标记。** 将原型代码放置在实际使用的位置附近（紧挨着其原型的模块或页面），以便上下文清晰明了——但请正确命名，使临时读者能一眼看出这是原型而非生产代码。对于抛弃型 UI 路由，遵循项目已有的任何路由约定；不要发明新的顶层结构。
2. **一条命令即可运行。** 遵循项目现有的任务运行器所支持的任何方式 — `pnpm <name>`，`python <path>`，`bun <path>` 等。用户必须能够无需思考直接启动它。
3. **默认不进行持久化。** 状态存在于内存中。持久化是原型要*检查*的内容，而不是它应该依赖的内容。如果问题明确涉及数据库，请使用临时数据库或本地文件，并加上明确的 "PROTOTYPE — wipe me" 命名。
4. **跳过精雕细琢。** 没有测试，除了让原型*可运行*之外没有错误处理，没有抽象。重点是快速获取认知。
5. **显化状态。** 在每次动作（逻辑）后或每次变体切换（UI）时，打印或渲染完整的相关状态，以便用户能够直观看到发生了什么变化。
6. **完成后进行捕获。** 将任何经过验证的决议整合到真实代码中，然后按照**原始凭据**的方式捕获原型本身：将其提交到一个独立于 main 的抛弃型分支，并在实现 issue 上留出指向该分支的上下文指针。同时在 issue 或 commit 中捕获答案（裁决结果及其解决的问题）。主分支只保留经过验证的决议。
