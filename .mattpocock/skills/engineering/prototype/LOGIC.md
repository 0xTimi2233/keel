# 逻辑原型（Logic Prototype）

一个微型交互式终端应用，允许用户手动驱动状态模型。当问题关注于**业务逻辑、状态迁移或数据形状**时使用——即在纸面上看起来很合理，但只有在推演真实用例时才能发现问题的那些设计。

## 适用场景

- "我不确定该状态机是否能处理先发生 X 再发生 Y 的边界情况。"
- "该数据模型是否真的能让我表示……的情况？"
- "我想在编写 API 之前切身体验一下 API 的设计应该是怎样的。"
- 任何用户希望**按按钮并观察状态变化**的场景。

如果问题是“这应该长成什么样”——分支选择错误。请使用 [UI.md](UI.md)。

## 流程

### 1. 阐明问题

在编写代码前，记录下你在对什么状态模型以及什么问题进行原型设计。在原型的 README 或文件顶部的注释中写下一段话。一个回答了错误问题的逻辑原型完全是浪费——将问题明确化，以便后续验证，无论用户是在线观察还是离线异步查看。

### 2. 选择语言

使用宿主项目所使用的任何语言。如果项目没有明显的运行时（例如文档仓库），请进行询问。

与项目现有的工具链约定保持一致——不要仅为了原型就引入新的包管理器或运行时。

### 3. 在便携式模块中隔离逻辑

将实际逻辑——即回答问题的核心部分——至于一个简短、纯粹的接口之后，以便将来可以将其抽取并直接放入真实代码库中。围绕它的 TUI 是可丢弃的；但逻辑模块不应是可丢弃的。

合适的形状取决于具体问题：

- **纯归约器（Pure reducer）** — `(state, action) => state`。适用于动作是离散事件且状态为单一值的情况。
- **状态机（State machine）** — 显式状态与迁移。适用于“当前哪些动作是合法的”本身就是问题的一部分的情况。
- **作用于简单数据类型的一组纯函数**。适用于没有隐式当前状态、只有数据转换的情况。
- **具有清晰方法暴露面的类或模块** — 适用于逻辑确实拥有持续内部状态的情况。

选择最适合所询问问题的形状，*而不是*最容易连接到 TUI 的形状。保持其纯粹性：无 I/O，无终端代码，无用于控制流的 `console.log`。TUI 导入它并对其进行调用；反向则没有任何数据流。

这就是使原型在其自身生命周期之外依然有用的原因：当问题得到解答时，经过验证的 reducer / 状态机 / 函数集可以单独抽离并合入真实模块中。

### 4. 构建展示状态的最小 TUI

将其构建为**轻量级 TUI** — 在每次 Tick 时，清空屏幕（`console.clear()` / `print("\033[2J\033[H")` / 等效方法）并重新渲染整个帧。用户应该始终看到一个稳定的视图，而不是不断增长的滚动回溯。

每一帧包含两个部分，按以下顺序：

1. **当前状态**，美化打印且易于比对 diff（每行一个字段，或格式化的 JSON）。对字段名或章节标题使用**加粗**，对次要上下文（时间戳、ID、派生值）使用**暗淡**。使用原生 ANSI 转义码即可 — `\x1b[1m` 加粗，`\x1b[2m` 暗淡，`\x1b[0m` 重置。除非项目已存在样式库，否则无需额外引入。
2. **快捷键列表**，列在底部：`[a] 添加用户  [d] 删除用户  [t] 推进时钟  [q] 退出`。加粗按键，暗淡描述，反之亦然 — 只要阅读清晰即可。

行为：

1. **初始化状态** — 单个内存对象/结构体。启动时渲染第一帧。
2. **每次读取一个按键（或一行）**，分发给修改状态的处理函数。
3. **在每次动作后重新渲染**完整帧 — 请勿追加，直接替换。
4. **循环直到退出。**

整个帧应能容纳在一个屏幕内。

### 5. 使其可通过一条命令运行

在项目现有的任务运行器中添加一个脚本（`package.json` 脚本，`Makefile`，`justfile`，`pyproject.toml`）。用户应该运行 `pnpm run <prototype-name>` 或等效命令 — 无需记住具体路径。

如果宿主项目没有任务运行器，只需将命令放在原型的 README 顶部。

### 6. 移交使用

将运行命令提供给用户。他们将自行进行操作；最有趣的时刻是当他们说“等等，这不应该可能发生”或“哈，我以为 X 会有所不同”时 — 这些都是*想法*本身中的 Bug，也是原型的终极意义所在。如果他们希望添加新动作，请添加它们。原型是在演进中发展的。

### 7. 捕获答案与原型

一旦原型回答了它的问题，捕获该答案，然后按照 [SKILL](SKILL.md) 中描述的方式捕获原型。逻辑特定的映射：经过验证的 reducer / 状态机 / 函数集抽离合入真实模块中（决议被吸收）；TUI 外壳则保留在抛弃型分支上，该分支将原型作为原始凭据进行保留。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型了。
- **不要将其连接到真实数据库。** 除非问题专门针对持久化，否则请使用内存存储。
- **不要泛化。** 不要考虑“如果我们以后想支持 X 怎么办”。原型只回答一个问题。
- **不要混淆逻辑与 TUI。** 如果 reducer / 状态机引用了 `console.log`、提示符或终端转义码，它就不再具备便携性。保持 TUI 作为纯模块之上的薄外壳。
- **不要将 TUI 外壳发布到生产环境。** 外壳专门针对终端手动驱动进行了优化。其背后的逻辑模块才是值得保留的部分。
