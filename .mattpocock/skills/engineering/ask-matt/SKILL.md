# Ask Matt

你无法记住每个技能，所以尽管提问。

**流程 (flow)** 是贯穿各个技能的路径。大多数路径沿着一条**主流程**推进，两条**汇入通道 (on-ramps)** 会汇入其中。其他所有技能都是独立的，或者是底层运行的词汇表层。

## 主流程：从构想至交付 (idea → ship)

大多数工作遵循的路线。你有一个构想，并希望将其构建出来。

1. **`/grill-with-docs`** — 通过访谈追问来锤炼构想。当你**拥有代码库**时由此开始：它是有状态的，会将学到的内容保留在 `CONTEXT.md` 和 ADR 中。（没有代码库？使用 `/grill-me` — 见“独立技能”。两者都运行相同的 `/grilling` 原语；`grill-with-docs` 是留存书面记录的那个。）
2. **分支 — 能否在对话中解决所有疑问？** 如果某个疑问需要可运行的答案（状态、业务逻辑、必须亲眼查看的 UI），可以通过原型开发进行迂回，两端均由 **`/handoff`** 进行衔接（参见“跨会话衔接”）：
   - 使用 **`/handoff`** 导出，针对该文件开启一个新的会话，
   - 使用 **`/prototype`** 编写抛弃型代码解答疑问，
   - 使用 **`/handoff`** 将所学内容带回，并在原始构想线程中对其进行引用。
3. **分支 — 这是多会话构建吗？**
   - **是** → **`/to-spec`**（将线程转化为规范文档），然后使用 **`/to-tickets`** 将其拆分为示踪弹工单，每张工单声明其**阻塞依赖**。在本地跟踪器上，这是 `.scratch/<feature>/issues/` 下每张工单对应一个文件，由人工按阻塞顺序优先处理；在真实跟踪器上，这些依赖变为原生阻塞链接，因此任何阻塞已解决的工单都可以被领取——针对每张工单启动 **`/implement`**，**并在每张工单之间清理上下文**。
   - **否** → 就在这里，在同一个上下文窗口中使用 **`/implement`**。

   无论哪种方式，**`/implement`** 都通过在内部驱动 **`/tdd`** 来构建每个 issue——一次完成一个红-绿切片——然后在提交之前运行 **`/code-review`**（对 diff 进行代码规范 + 需求规范的双轴审查）来收尾。当你只想以测试驱动的方式构建具体行为而不需要完整规范时，可以单独使用 **`/tdd`**；当你希望针对固定基点审查分支或 PR 时，可以单独使用 **`/code-review`**。

### 上下文卫生 (Context hygiene)

将步骤 1–3 保持在**一个连贯的上下文窗口**中——在 `/to-tickets` 完成之前不要压缩或清理——这样追问探究、规范编写和工单拆解都建立在相同的思考基础之上。随后每个 `/implement` 都将从工单开始全新启动。

此过程的上限是**[智能区 (smart zone)](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：即模型仍然能保持敏锐推理能力的窗口（在前沿模型上约为 ~120k tokens）。如果会话在 `/to-tickets` 之前接近该上限，请勿在性能衰退的情况下硬推——使用 `/handoff` 并在新线程中继续。

## 汇入通道 (On-ramps)

产生工作并随后汇入主流程的起始场景。

- **Bug 和需求堆积** → **`/triage`**。它驱动 issue 穿过分流角色，并生成代理就绪 (agent-ready) 的 issue，稍后由 **`/implement`** 领取。

  分流仅适用于**非你创建**的 issue——Bug 报告、传入的功能需求、任何原始到达的内容。`/to-tickets` 生成的工单已经是代理就绪的，因此**无需对其进行分流**。

- **某物损坏/报错** → **`/diagnosing-bugs`**。适用于疑难问题：看一眼无法解决的 Bug、间歇性闪烁测试、在两个已知正常状态之间悄悄引入的衰退。在拥有**紧凑反馈循环**（在*当前* Bug 上已能触发报错的单一命令）之前，它拒绝凭空推测，然后附带回归测试进行修复。当真实的发现是缺乏良好的接缝来锁定 Bug 时，其事后剖析 (post-mortem) 会交接给 **`/improve-codebase-architecture`**。

- **庞大且迷雾重重的工程——全新项目或超大功能构建，单个会话容纳不下** → **`/wayfinder`**，这是这里认知要求最高的流程。当从当前通往目标的路径尚不可见时，它会在 issue 跟踪器上绘制一张由**决策工单**组成的**共享地图**，并逐一解决它们——产生的是**决策，而非交付物**——直到迷雾退去、路径清晰。**`/grill-with-docs`** 锤炼的是单个会话即可容纳的构想，而 wayfinder 则针对无法容纳的构想——它更慢、更密集，因此请务必仅在确有必要时使用，切勿用于范围明确的功能。

  当地图清晰时，**它会进行交接，而不是直接构建**：在 **`/to-spec`** 处汇入主流程，将地图中相互关联的决策折叠为可构建的计划，然后像往常一样使用 `/to-tickets` 和 `/implement`。将地图直接循环接入 `/implement` 会跳过折叠步骤并抛弃关联细节——只有当工作量经证实确实微小时，才直接前往 `/implement`。

## 代码库健康 (Codebase health)

非功能开发——日常维护。

- **`/improve-codebase-architecture`** — 只要你有空闲时间就可以运行，以保持代码库良好利于代理操作。它能浮现**深化改进机会**；选择其中一个会*生成一个构想*，你可以将其带入 `/grill-with-docs` 的主流程中。它是寻找候选方案的调查工具；下文的 **`/codebase-design`** 则是你在上面设计所选方案的工作台。

## 底层词汇表 (Vocabulary underneath)

运行在其他技能*之下*的两个模型自主调用参考——各自为其词汇表的单一事实来源。当问题在于**用词**而非流程时，可以直接使用它们；或者让上面的技能将它们引入。

- **`/domain-modeling`** — 锤炼项目的*领域*语言：挑战模糊术语，解决过载词汇（例如“账号”承担了三种职责），将难以逆转的决策记录为 ADR。它是 `/grill-with-docs` 所驱动的主动规范，用于保持 `CONTEXT.md` 为一份干净的词汇表。
- **`/codebase-design`** — 用于设计模块*形状*的深层模块词汇表（模块、接口、深度、接缝、适配器、杠杆力、局部性）：在干净接缝的小接口背后提供大量行为。`/tdd` 和 `/improve-codebase-architecture` 都能使用该词汇表。

## 跨会话衔接 (Crossing sessions)

- **`/handoff`** — 当线程已满或你需要分支拆分（例如进入 `/prototype` 会话）时，这会将对话压缩为 markdown 文件。你不会在原位继续——你**开启一个新会话并引用该文件**以跨会话传递上下文。它是两个上下文窗口之间的双向桥梁。当你需要**全新会话**但又需要**保留当前对话**时使用它。
- **`/compact`** (内置) — 留在**同一个对话**中，让早期的轮次被总结摘要。在**阶段之间有意的停顿**时使用，前提是你不在乎丢失逐字历史。不要在阶段中途压缩——代理可能会迷失方向。`/handoff` 派生分叉；`/compact` 原地继续。

## 独立技能 (Standalone)

完全脱离主流程。

- **`/grill-me`** — 与 `/grill-with-docs` 相同的不懈追问访谈，但用于你**没有代码库**的场景。无状态：它不在本地保存任何内容，也不构建 `CONTEXT.md`。用它来锤炼任何不保存在仓库中的计划或设计。
- **`/prototype`** — 一个回答单个设计疑问的小型抛弃型程序：该状态模型感觉是否合适，或者 UI 应该是什么样子。从第一天起就是抛弃型的——保留答案，删除代码。它是主流程步骤 2 中的迂回路线，但任何时候当设计疑问难以在纸面上定论时都可以使用它。
- **`/research`** — 将阅读调查工作委托给**后台代理**：它针对**权威来源**调查问题，然后在仓库中留下一个带引用的 Markdown 文件。在其阅读时继续你的工作。它生成的文件可以带*入* `/grill-with-docs` 的主流程中——调研为思考提供养分，但不能取代思考。
- **`/teach`** — 使用当前目录作为有状态的工作区，跨多个会话学习一个概念。
- **`/writing-great-skills`** — 编写和编辑优质技能的参考指南。

## 前置条件 (Precondition)

**`/setup-matt-pocock-skills`** — 在你的第一个工程流程之前运行，配置其他技能所假定的 issue 跟踪器、分流标签和文档布局。自定义 issue 跟踪器也同样适用。
