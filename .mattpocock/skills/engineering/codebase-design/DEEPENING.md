# 模块深化 (Deepening)

基于依赖关系，如何安全地深化一组浅层模块 (shallow modules)。本文假设读者已掌握 [SKILL.md](SKILL.md) 中的词汇表——**模块 (module)**、**接口 (interface)**、**接缝 (seam)**、**适配器 (adapter)**。

## 依赖分类 (Dependency categories)

在评估模块深化的候选对象时，应对其依赖关系进行分类。分类决定了深化后的模块如何跨其接缝进行测试。

### 1. 进程内依赖 (In-process)

纯计算、内存状态、无 I/O。始终可以深化——合并这些模块并直接通过新接口进行测试。无需适配器。

### 2. 本地可替代依赖 (Local-substitutable)

拥有本地测试替代品（例如用于 Postgres 的 PGLite、内存文件系统）的依赖。只要替代品存在即可进行深化。深化后的模块在测试中使用运行在测试套件中的替代品进行测试。接缝是内部的；模块的外部接口处无需声明端口 (port)。

### 3. 远程但自控依赖 (Remote but owned - 六边形架构/端口与适配器)

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个 **端口 (port)**（接口）。深层模块拥有核心逻辑；传输层作为 **适配器 (adapter)** 被注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

推荐方案范例：*"在接缝处定义一个端口，为生产环境实现 HTTP 适配器，为测试实现内存适配器，这样即便跨网络部署，逻辑也完整保留在一个深层模块中。"*

### 4. 真实外部依赖 (True external - Mock)

你无法控制的第三方服务（Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口接收；测试提供 Mock 适配器。

## 接缝规范 (Seam discipline)

- **单个适配器意味着假想接缝。两个适配器才意味着真实接缝。** 除非至少有两个适配器成立（通常是生产环境 + 测试），否则不要引入端口。只有单个适配器的接缝只是单纯的间接引用。
- **内部接缝 vs 外部接缝。** 一个深层模块既可以拥有内部接缝（对其实现私有，由其自身的测试使用），也可以在其接口处拥有外部接缝。不要仅仅因为测试使用了内部接缝就将其通过公开接口暴露出来。

## 测试策略：替换，而非叠加 (Testing strategy: replace, don't layer)

- 一旦在深化模块的接口层建立了测试，针对旧浅层模块的旧单元测试就变成了浪费——直接删除它们。
- 在深化模块的接口层编写新测试。**接口即测试表面 (interface is the test surface)**。
- 测试对通过接口可观察到的结果进行断言，而不是针对内部状态断言。
- 测试应当能在内部重构中幸存——它们描述的是行为，而非实现。如果实现改变时测试也必须修改，说明测试穿透了接口。
