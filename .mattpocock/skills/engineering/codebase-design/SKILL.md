# 代码库设计 (Codebase Design)

设计**深层模块 (deep modules)**：在干净的接缝处，将大量的行为隐藏在小型的接口之后，并且可以通过该接口进行测试。无论在何处进行代码设计或结构重构，请使用此处的语言和原则。其目标是为调用者提供**杠杆力 (leverage)**，为维护者提供**局部性 (locality)**，并为每个人提供**可测试性 (testability)**。

## 词汇表 (Glossary)

请精确使用这些术语——不要用“组件 (component)”、“服务 (service)”、“API”或“边界 (boundary)”来替代。统一语言是本技能的核心价值所在。

**模块 (Module)** — 任何拥有接口和实现的实体。故意保持与规模无关：可以是一个函数、类、包或跨层切片。*避免使用*：单元 (unit)、组件 (component)、服务 (service)。

**接口 (Interface)** — 调用者为了正确使用该模块所必须了解的一切：类型签名，还包括不变式 (invariants)、顺序约束、错误模式、必需配置以及性能特征。*避免使用*：API、签名 (signature)（过于狭隘——它们仅指代类型层面的表面）。

**实现 (Implementation)** — 模块内部的内容，即代码主体。与 **适配器 (Adapter)** 不同：一个事物可以是带有庞大实现的较小适配器（如 Postgres 仓储），也可以是带有微小实现的较大适配器（如内存 Fake）。当焦点在于接缝时，使用“适配器”；其他情况下使用“实现”。

**深度 (Depth)** — 接口处的杠杆力：调用者（或测试）每掌握一个单位的接口所能调动的行为量。当大量的行为隐藏在小型接口背后时，模块即为**深层 (deep)** 的；当接口几乎与实现一样复杂时，模块即为**浅层 (shallow)** 的。

**接缝 (Seam)** _(Michael Feathers)_ — 无需在该处编辑代码即可改变行为的位置；即模块接口所在的位置。接缝放在哪里本身就是一项独立的设计决策，与其背后容纳的内容不同。*避免使用*：边界 (boundary)（与 DDD 的受限上下文混淆过载）。

**适配器 (Adapter)** — 在接缝处满足接口的具体事物。描述的是*角色*（填补什么槽位），而非实体（内部是什么）。

**杠杆力 (Leverage)** — 调用者从深度中获取的好处：每掌握一个单位的接口即可获得更多的能力。一个实现即可在 N 个调用点和 M 个测试中获得回报。

**局部性 (Locality)** — 维护者从深度中获取的好处：变更、Bug、知识和验证均集中在一个地方，而不是散落分发在各个调用者中。修复一次，到处受益。

## 深层 vs 浅层 (Deep vs shallow)

**深层模块 (Deep module)** = 小型接口 + 丰富实现：

```
┌─────────────────────┐
│    小型接口 (Small) │  ← 少数方法，简单参数
├─────────────────────┤
│                     │
│  深层实现 (Deep)    │  ← 隐藏复杂的逻辑
│                     │
└─────────────────────┘
```

**浅层模块 (Shallow module)** = 大型接口 + 贫乏实现（应当避免）：

```
┌─────────────────────────────────┐
│       大型接口 (Large)          │  ← 繁多方法，复杂参数
├─────────────────────────────────┤
│  薄透实现 (Thin)                │  ← 仅做纯粹的透传
└─────────────────────────────────┘
```

在设计接口时，问问自己：

- 我能否减少方法的数量？
- 我能否简化参数？
- 我能否在内部隐藏更多的复杂性？

## 设计原则 (Principles)

- **深度是接口的属性，而不是实现的属性。** 一个深层模块可以在内部由小型、可 Mock、可替换的零部件组成——它们只是不属于接口的一部分而已。一个模块既可以拥有**内部接缝**（对其实现私有，由其自身的测试使用），也可以在其接口处拥有**外部接缝**。
- **删除测试法 (The deletion test)。** 试想删除该模块。如果复杂性直接凭空消失，说明它只是个透传模块。如果复杂性重新散落暴露在 N 个调用者中，说明它确实物有所值。
- **接口即测试表面 (The interface is the test surface)。** 调用者与测试穿过的是同一个接缝。如果你想要*穿透*接口去测试内部，该模块的形状大概率设计错了。
- **单个适配器意味着假想接缝。两个适配器才意味着真实接缝。** 除非在接缝两侧确实存在差异化的变体，否则不要引入接缝。

## 为可测试性而设计 (Designing for testability)

良好的接口使测试水到渠成：

1. **接收依赖，而不是创建依赖。**

   ```typescript
   // 易于测试
   function processOrder(order, paymentGateway) {}

   // 难以测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，而不是产生副作用。**

   ```typescript
   // 易于测试
   function calculateDiscount(cart): Discount {}

   // 难以测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **较小的表面积。** 更少的方法 = 需要更少的测试。更少的参数 = 更简单的测试 setup。

## 概念关系 (Relationships)

- 一个 **模块 (Module)** 恰好拥有一个 **接口 (Interface)**（它向调用者和测试展现的表面）。
- **深度 (Depth)** 是 **模块 (Module)** 针对其 **接口 (Interface)** 衡量的属性。
- **接缝 (Seam)** 是 **模块 (Module)** 的 **接口 (Interface)** 所在的位置。
- **适配器 (Adapter)** 位于 **接缝 (Seam)** 处并满足 **接口 (Interface)**。
- **深度 (Depth)** 为调用者带来 **杠杆力 (Leverage)**，为维护者带来 **局部性 (Locality)**。

## 拒绝的表述 (Rejected framings)

- **将深度定义为实现代码行数与接口代码行数的比例** (Ousterhout)：这会惩罚精简代码并鼓励虚增实现代码。我们改用“深度即杠杆力”的概念。
- **将“接口”狭隘理解为 TypeScript `interface` 关键字或类的 public 方法**：过于狭隘——这里的接口包含调用者必须了解的一切事实。
- **“边界 (Boundary)”**：与 DDD 的受限上下文混淆过载。请使用 **接缝 (seam)** 或 **接口 (interface)**。
