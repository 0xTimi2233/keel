# 两次设计 (Design It Twice)

当用户希望针对选定的模块深化候选对象探索替代接口方案时，请使用此并行子代理模式。基于“两次设计 (Design It Twice)”原则（John Ousterhout）——你的第一个想法往往不太可能是最好的。

使用 [SKILL.md](SKILL.md) 中的词汇表——**模块 (module)**、**接口 (interface)**、**接缝 (seam)**、**适配器 (adapter)**、**杠杆力 (leverage)**。

## 流程

### 1. 界定问题空间 (Frame the problem space)

在启动子代理之前，为选定的候选对象向用户撰写一份关于问题空间的说明：

- 任何新接口都需要满足的约束条件
- 它将依赖的依赖项，以及它们属于哪种分类（参见 [DEEPENING.md](DEEPENING.md)）
- 用于充实约束条件的草略示例代码草图——这不是方案提案，只是为了让约束更加具体

将这些展示给用户，然后立即进入步骤 2。在子代理并行工作的过程中，用户可以同步阅读和思考。

### 2. 启动子代理 (Spawn sub-agents)

使用 Agent 工具并行启动 3 个或更多子代理。每个子代理必须为深化后的模块产出一个**截然不同**的接口设计。

为每个子代理提供独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖分类、接缝背后的内容）。该简报独立于步骤 1 中面向用户的问题空间说明。为每个代理指定不同的设计约束：

- 代理 1："极简接口——目标最多 1–3 个入口点。最大化每个入口点的杠杆力。"
- 代理 2："最大化灵活性——支持多种使用场景和扩展能力。"
- 代理 3："针对最常见的调用者进行优化——使默认场景变得极其简单。"
- 代理 4（如适用）："围绕端口与适配器进行设计，以应对跨接缝的依赖关系。"

简报中必须包含 [SKILL.md](SKILL.md) 词汇表和 CONTEXT.md 词汇表，以便每个子代理在命名时与架构语言和项目的领域语言保持一致。

每个子代理输出：

1. 接口（类型、方法、参数——加上不变式、顺序要求、错误模式）
2. 展示调用者如何使用它的使用示例
3. 实现细节隐藏在接缝背后的内容
4. 依赖策略与适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡分析——哪里杠杆力高，哪里杠杆力薄弱

### 3. 展示与对比 (Present and compare)

按顺序展示各个设计方案，以便用户能够消化吸收每一个方案，然后使用文字对它们进行对比。从**深度 (depth)**（接口处的杠杆力）、**局部性 (locality)**（变更集中的位置）以及**接缝位置**等维度进行对比。

在对比之后，给出你自己的建议：你认为哪个设计最强以及原因。如果不同设计的元素结合起来效果更好，可以提出一个混合方案。保持明确见解——用户需要的是有说服力的专业见解，而不是无所适从的菜单。
