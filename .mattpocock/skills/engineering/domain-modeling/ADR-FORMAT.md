# ADR (架构决策记录) 格式

ADR 保存在 `docs/adr/` 目录中，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

延迟创建 `docs/adr/` 目录 — 仅在需要记录第一个 ADR 时才创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么这样决定。}
```

就这么简单。一份 ADR 可以只有单个段落。其价值在于记录*做了*什么决策以及*为什么*——而不是在于填满各个模板章节。

## 可选章节

仅在确实能提供实际价值时包含以下内容。大多数 ADR 并不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 在重新评估决策时很有用
- **Considered Options（考虑过的选项）** — 仅在被拒绝的替代方案值得被记住时使用
- **Consequences（后果/影响）** — 仅在需要特别指出非显而易见的下游影响时使用

## 编号规则

扫描 `docs/adr/` 查找已存在的最大编号，并加 1。

## 何时提供/编写 ADR

以下三条必须**同时成立**：

1. **难以逆转** — 以后改变主意的成本非常高昂
2. **缺乏上下文时令人困惑/意外** — 未来的读者看到代码时会困惑“他们究竟为什么要这样做？”
3. **真实权衡取舍的结果** — 存在切实可行的替代方案，且你出于特定原因选择了其中之一

如果一项决策很容易逆转，跳过它 — 你以后直接逆转即可。如果不令人意外，没有人会追问原因。如果没有真正的替代方案，除了“我们做了显而易见的事”之外没有任何东西值得记录。

### 什么样的决策符合条件

- **架构形态。** “我们正在使用 Monorepo。”“写入模型是事件溯源 (event-sourced) 的，读取模型投影到 Postgres 中。”
- **上下文之间的集成模式。** “订单 (Ordering) 和账单 (Billing) 通过领域事件进行通信，而不是同步 HTTP。”
- **带有锁定效应的技术选型。** 数据库、消息总线、身份认证提供方、部署目标。并非每个库都需要 — 仅针对那些需要花上一个季度才能替换掉的库。
- **边界与范围决策。** “客户数据归 Customer 上下文所有；其他上下文仅通过 ID 对其进行引用。” 明确的“否定”与“肯定”同样具有价值。
- **偏离显而易见路径的有意为之。** “出于 X 原因，我们使用手动 SQL 代替 ORM。” 任何合理读者都会做出相反假设的情况。这些记录能防止下一位工程师去“修复”某个原本就是故意为之的设计。
- **代码中不可见的约束条件。** “由于合规要求，我们无法使用 AWS。” “由于合作伙伴 API 的契约规定，响应时间必须在 200ms 以内。”
- **被拒绝的替代方案（当拒绝原因非显而易见时）。** 如果你考虑了 GraphQL 并出于微妙的原因选择了 REST，请将其记录下来 — 否则六个月后会有人再次提议使用 GraphQL。
