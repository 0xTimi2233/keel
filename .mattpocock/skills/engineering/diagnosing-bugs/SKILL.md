# 诊断 Bug (Diagnosing Bugs)

一套针对疑难 Bug 的严谨规范。除非有明确合理的依据，否则请勿跳过任何阶段。

在探索代码库时，阅读 `CONTEXT.md`（如果存在）以获取相关模块清晰的心智模型，并检查你所触及领域的 ADR。

## 阶段 1 — 建立反馈循环 (Build a feedback loop)

**本技能的核心就在于此。** 其他一切都是机械性的。如果你针对该 Bug 拥有一个**紧凑的**通过/失败信号——一个能在*当前* Bug 上触发报错 (go red) 的信号——你就一定能找到原因；二分法、假设检验和埋点/仪表化都只是使用这一信号而已。如果你没有这样的信号，看再久的代码也无济于事。

在此投入不成比例的巨大精力。**要激进。要有创造力。绝不轻言放弃。**

### 构建反馈循环的方法 — 大致按以下顺序尝试

1. 能够触及该 Bug 的任何接缝处的**失败测试** — 单元测试、集成测试、端到端测试。
2. 针对运行中开发服务器的 **Curl / HTTP 脚本**。
3. 带有 Fixture 输入的 **CLI 调用**，将 stdout 与已知正常的快照进行 diff 比对。
4. **无头浏览器脚本** (Playwright / Puppeteer) — 驱动 UI，对 DOM/控制台/网络进行断言。
5. **重放捕获的追踪记录 (trace)。** 将真实的网络请求 / 载荷 (payload) / 事件日志保存到磁盘；在隔离环境下通过代码路径重放。
6. **抛弃型测试脚手架 (Throwaway harness)。** 启动系统的最小子集（一个服务、Mock 依赖），只需一次函数调用即可执行触发 Bug 的代码路径。
7. **属性/模糊测试循环 (Property / fuzz loop)。** 如果 Bug 是“偶尔输出错误”，运行 1000 次随机输入并查找失败模式。
8. **二分法脚手架 (Bisection harness)。** 如果 Bug 出现在两个已知状态（commit、数据集、版本）之间，将“在状态 X 下启动、检查、重复”自动化，以便能够通过 `git bisect run` 运行它。
9. **差异对比循环 (Differential loop)。** 通过旧版本 vs 新版本（或两种配置）运行相同的输入，并对输出进行 diff 比对。
10. **HITL (人机回环) bash 脚本。** 万不得已的手段。如果必须由人工点击，使用 `scripts/hitl-loop.template.sh` 驱动*人工*，使循环依然保持结构化。捕获的输出将反馈给你。

构建好正确的反馈循环，Bug 就已经修复了 90%。

### 紧凑化反馈循环 (Tighten the loop)

将反馈循环视为一款产品。一旦你拥有了*一个*循环，就去**紧凑化**它：

- 我能否让它更快？（缓存 setup、跳过无关的初始化、收窄测试范围。）
- 我能否让信号更敏锐？（断言特定的症状，而不是“没有崩溃”。）
- 我能否让它更具备确定性？（固定时间、设置随机种子、隔离文件系统、冻结网络。）

一个耗时 30 秒且结果闪烁不稳定 (flaky) 的循环仅比没有循环好一点点；而一个耗时 2 秒且确定性极高 (deterministic) 的循环则是紧凑的——这是调试中的超级利器。

### 非确定性 Bug (Non-deterministic bugs)

目标不是获得一个干净的单次重现，而是获得**更高的重现率**。将触发逻辑循环运行 100 次、进行并行化、增加压力、收窄时间窗口、注入 sleep。一个 50% 概率闪烁报错的 Bug 是可调试的；而 1% 概率的则不可调试——持续提升重现率，直到其变得可调试。

### 当你真正无法构建反馈循环时

停下来并明确告知用户。列出你尝试过的所有方法。向用户请求：(a) 访问能够重现该问题的任何环境，(b) 捕获的产物（HAR 文件、日志 Dump、Core Dump、带时间戳的屏幕录像），或 (c) 允许添加临时生产环境埋点。在没有反馈循环的情况下，**切勿**直接继续进行假设推断。

### 完成标准 — 一个触发报错的紧凑反馈循环

当反馈循环达到**紧凑**且**具备报错能力 (red-capable)** 时，阶段 1 结束：你能指出**一个具体命令** — 脚本路径、测试调用、curl — 且你**已经至少运行过一次**（粘贴调用命令及其输出），并且它满足：

- [ ] **具备报错能力 (Red-capable)** — 它能够驱动真实的 Bug 代码路径，并对**用户的确切症状**进行断言，因此它能在当前 Bug 上触发报错 (go red)，并在修复后恢复正常 (go green)。绝非单纯“无错运行” — 它必须能够*捕获这一个特定的 Bug*。
- [ ] **确定性 (Deterministic)** — 每次运行 verdict 一致（针对闪烁报错 Bug：如上所述，拥有固定且高概率的重现率）。
- [ ] **快速 (Fast)** — 耗时数秒，而非数分钟。
- [ ] **代理可运行 (Agent-runnable)** — 你可以无人值守运行它；人机回环仅通过 `scripts/hitl-loop.template.sh` 进行。

如果你发现在存在该命令之前，你就在阅读代码尝试构建理论，**请停下 — 直接跳到假设阶段正是本技能旨在防止的典型失败行为。** 没有具备报错能力的命令，就没有阶段 2。

## 阶段 2 — 重现 + 精简 (Reproduce + minimise)

运行反馈循环。观察它触发报错 — Bug 浮现。

确认：

- [ ] 反馈循环产生了**用户**所描述的失败模式 — 而不是恰好在附近的另一种失败。找错 Bug = 修复错误。
- [ ] 失败在多次运行中可重现（或者对于非确定性 Bug，重现率足够高以供调试）。
- [ ] 你已捕获确切的症状（错误信息、错误输出、卡顿耗时），以便后续阶段能够验证修复确实解决了该症状。

### 精简 (Minimise)

一旦触发报错，将重现场景收缩为**仍能触发报错的最简单场景**。**一次一个**地删减输入、调用方、配置、数据和步骤，每次删减后重新运行反馈循环 — 仅保留对失败起承重作用 (load-bearing) 的元素。

为什么要费此周折：精简的重现场景能在阶段 3 中收缩假设空间（剩下的可疑活动部件更少），并在阶段 5 中成为干净的回归测试。

当**所有保留的元素都起承重作用**时完成 — 移除其中任何一个都会使反馈循环恢复正常 (go green)。

在完成重现**以及**精简之前，不要进入下一阶段。

## 阶段 3 — 假设推断 (Hypothesise)

在测试任何假设之前，生成 **3–5 个按优先级排序的假设**。仅生成单一假设会导致思维锚定在第一个看起来合理的想法上。

每个假设必须是**可证伪的 (falsifiable)**：明确指出其做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 将使 Bug 消失 / <改变 Z> 将使问题恶化。"

如果你无法写出预测，说明该假设只凭直觉 — 请予以废弃或锤炼明确。

**在测试之前将排序后的假设列表展示给用户。** 用户通常拥有可立即可重排的领域知识（“我们刚刚发布了针对 #3 的变更”），或者知道他们已经排除的假设。廉价的 Checkpoint，巨大的时间节省。但不要死扣等待 — 如果用户离开桌面 (AFK)，请按你的排序继续推进。

## 阶段 4 — 埋点/仪表化 (Instrument)

每个探针 (probe) 必须映射到阶段 3 中的特定预测。**一次仅改变一个变量。**

工具偏好：

1. **调试器 / REPL 检查**（如果环境支持）。一个断点胜过十条日志。
2. 区分不同假设的边界处的**针对性日志**。
3. 绝不“记录所有日志然后 grep”。

**为每条调试日志打上带唯一前缀的标签**，例如 `[DEBUG-a4f2]`。结束时的清理工作会变成一次简单的 grep。无标签日志容易遗留；有标签日志必被清理。

**性能分支。** 对于性能衰退问题，日志通常是误导性的。正确的做法：建立基准测量（耗时测试脚手架、`performance.now()`、Profiler、查询计划 (query plan)），然后进行二分定位。先测量，后修复。

## 阶段 5 — 修复 + 回归测试 (Fix + regression test)

**在修复之前**编写回归测试 — 但前提是存在**正确的接缝**。

正确的接缝是指测试能够在调用点执行**真实的 Bug 模式**。如果唯一可用的接缝过于浅显（Bug 需要多个调用方时仅有单调用方测试，单元测试无法复现触发 Bug 的链条），在该处添加回归测试会给出虚假的安全感。

**如果不存在正确的接缝，这本身就是一项调查发现。** 请记录下来。说明代码库架构阻碍了锁定 Bug。为下一阶段打上标记。

如果存在正确的接缝：

1. 将精简后的重现场景转化为该接缝处的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未精简）场景重新运行阶段 1 的反馈循环。

## 阶段 6 — 清理 + 事后剖析 (Cleanup + post-mortem)

在声明完成之前必须满足：

- [ ] 原始重现场景不再重现（重新运行阶段 1 循环）
- [ ] 回归测试通过（或记录了接缝缺失）
- [ ] 已移除所有 `[DEBUG-...]` 埋点（`grep` 探查前缀）
- [ ] 已删除抛弃型原型（或移动到标记清晰的调试目录）
- [ ] 在 commit / PR 信息中说明了证实正确的假设 — 以便下一个调试者学习

**然后问：什么本来可以防止这个 Bug？** 如果答案涉及架构变更（没有良好的测试接缝、交织错乱的调用方、隐藏的耦合），请将具体细节交接给 `/improve-codebase-architecture` 技能。在修复**完成之后**提出建议，而不是在之前 — 因为你现在掌握的信息比刚开始时要多得多。
