# 转化为规范（To Spec）

本 Skill 提取当前的对话上下文和代码库理解，并生成一份规范说明 spec（你可能将该文档称为 PRD）。**不要**对用户进行面试 — 只需综合你已经了解的内容。

应该已向你提供了 issue 追踪器和分类标签词汇表 — 如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你尚未探索代码库，探索仓库以了解代码库的当前状态。在整个 spec 中使用项目的领域词汇表术语，并尊重你所触及区域中的所有 ADR。

2. 勾勒出你将要对功能进行测试的接缝（seams）。相比新的接缝，应该优先选用现有的接缝。使用尽可能高层级的接缝。如果需要新接缝，在你可以达到的最高点提出它们。跨越代码库的接缝越少越好 - 理想的数量是一个。

与用户确认这些接缝符合他们的预期。

3. 使用下面的模板编写 spec，然后将其发布到项目的 issue 追踪器。应用 `ready-for-agent` 分类标签 - 无需额外的分类。

<spec-template>

## 问题陈述（Problem Statement）

用户面临的问题，站在用户的视角。

## 解决方案（Solution）

问题的解决方案，站在用户的视角。

## 用户故事（User Stories）

一份**长而带编号**的用户故事列表。每个用户故事的格式应为：

1. 作为一名 <角色/actor>，我想要 <功能/feature>，以便于 <收益/benefit>

<user-story-example>
1. 作为一名手机银行客户，我想要查看账户余额，以便于对我的消费做出更好的明智决策
</user-story-example>

这份用户故事列表应该非常详尽，涵盖该功能的方方面面。

## 实现决议（Implementation Decisions）

已做出的实现决议列表。这可以包括：

- 将要构建/修改的模块
- 将要修改的那些模块的接口
- 来自开发者的技术澄清
- 架构决议
- Schema 变更
- API 契约
- 具体交互

**不要**包含具体的文件路径或代码片段。它们可能会很快过时。

例外：如果某个原型产生了一个能比散文更精准地编码决议的代码片段（状态机、reducer、schema、类型形状），请将其内联在相关决议中，并简要注明它来自于原型。裁剪至包含丰富决议的部分 — 不是可运行的 Demo，仅保留核心关键部分。

## 测试决议（Testing Decisions）

已做出的测试决议列表。包括：

- 关于什么是好测试的描述（仅测试外部行为，而非实现细节）
- 将测试哪些模块
- 测试的先前艺术/先例（即代码库中类似类型的测试）

## 范围之外（Out of Scope）

关于本规范范围之外的事项的描述。

## 进一步补充（Further Notes）

关于该功能的任何进一步补充说明。

</spec-template>
