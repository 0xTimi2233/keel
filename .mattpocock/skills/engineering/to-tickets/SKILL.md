# 转化为工单（To Tickets）

将计划、spec 或对话拆分为一组**工单（tickets）** — 弹道子弹（tracer-bullet）垂直切片，每张工单声明**阻塞**它的其他工单。

应该已向你提供了 issue 追踪器和分类标签词汇表 — 如果没有，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文中已有的任何内容开展工作。如果用户传入一个引用（spec 路径、issue 编号或 URL）作为参数，获取它并阅读其完整的正文和评论。

### 2. 探索代码库（可选）

如果你尚未探索代码库，探索以理解代码的当前状态。工单标题和描述应使用项目的领域词汇表术语，并尊重你所触及区域中的 ADR。

寻找对代码进行预重构（prefactor）的机会，以使实现更容易。"先让变更变得容易，然后再进行容易的变更。"（Make the change easy, then make the easy change.）

### 3. 草拟垂直切片

将工作拆分为**弹道子弹（tracer bullet）**工单。

<vertical-slice-rules>

- 每个切片穿透每一层（schema, API, UI, 测试），切出一条狭窄但**完整**的路径 — 是垂直切片，而**非**单一层的水平切片
- 完成的切片本身是可以演示或验证的
- 每个切片的尺寸应设计为适合容纳在单个全新的上下文窗口中
- 任何预重构工作都应该首先完成

</vertical-slice-rules>

为每张工单指定其**阻塞边（blocking edges）** — 即在该工单开始前必须完成的其他工单。没有阻塞方的工单可以立即开始。

**宽泛重构（wide refactors）是垂直切片的例外。** **宽泛重构**是指一种机械化的变更 — 重命名列、重新给共享符号定义类型 — 它的**爆炸半径**扇面覆盖整个代码库，因此单次修改就会一次性破坏成千上万个调用点，没有任何垂直切片能保持绿色通过。不要强行将其塞入弹道子弹中；按照**扩展–收缩（expand–contract）**进行排序。首先扩展：在旧形式旁边添加新形式，这样不会破坏任何内容。然后按爆炸半径划分的批次（按包、按目录）将调用点迁移过来，每批都是各自的工单，被扩展工单所阻塞，由于旧形式依然存在，各批次间能保持 CI 为绿色。最后收缩：一旦没有任何调用者留存，在被每个迁移批次所阻塞的工单中删除旧形式。当连批次本身都无法独立保持绿色时，保持序列不变，但让他们共享一个集成分支，这些批次共同阻塞最终的“集成与验证”工单 — 仅在该最终工单中承诺绿色通过。

### 4. 询问用户

将拟议的拆解方案展示为带编号的列表。对于每张工单，展示：

- **标题（Title）**：简短描述性名称
- **阻塞方（Blocked by）**：必须首先完成的其他工单（如果有）
- **交付内容（What it delivers）**：该工单使之正常工作的端到端行为

询问用户：

- 粒度感觉合适吗？（太粗 / 太细）
- 阻塞边是否正确 — 每张工单是否仅依赖真正门控它的工单？
- 是否应该对任何工单进行合并或进一步拆分？

迭代直到用户批准拆解方案。

### 5. 将工单发布到配置的追踪器

发布已批准的工单。**如何发布**取决于 `/setup-matt-pocock-skills` 配置的追踪器 — 两种方式下的工单内容相同，仅阻塞边的形式有所改变：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单写入一个文件，按依赖顺序（阻塞方在前）从 `01` 开始编号。每个文件的 "Blocked by" 列出其依赖的编号/标题。使用下面的单工单文件模板 — 每文件一张工单，切勿使用单个合并文件。
- **真实 issue 追踪器 (GitHub, Linear, …)** → 按依赖顺序（阻塞方在前）每张工单发布一个 issue，以便每张工单的阻塞边可以引用真实的标识符。在平台拥有原生阻塞 / 子 issue 关系时使用它；否则将每张工单的 "Blocked by" 设置为阻塞 issue。除非另有指示，否则应用 `ready-for-agent` 分类标签 — 工单凭构造即可由 Agent 领取。

针对**前沿（frontier）**开展工作：任何阻塞方已全部完成的工单。对于纯线性链，这意味着从上到下。

切勿关闭或修改任何父 issue。
