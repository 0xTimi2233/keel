# 测试驱动开发（Test-Driven Development）

TDD 即“红 → 绿”循环。本 Skill 是使该循环产生值得保留的测试的参考标准：什么是好测试、测试应该加在哪里、反模式以及循环规则。每个章节在每个循环周期中都适用 — 在循环之前和循环期间查阅它们，而不是在循环结束后。

在探索代码库时，阅读 `CONTEXT.md`（如果存在），以便测试名称和接口词汇匹配项目的领域语言，并尊重你所触及区域中的 ADR。

## 什么是好的测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以完全重构变动；测试不应该变动。一个好的测试读起来就像一份规范说明 — "user can checkout with valid cart"（用户可以使用有效购物车进行结账）会确切地告诉你存在什么能力 — 并且在重构中幸存下来，因为它关心的是行为而非内部结构。

查看 [tests.md](tests.md) 获取示例，查看 [mocking.md](mocking.md) 获取 Mock 指南。

## 接缝（Seams）— 测试应该放在哪里

**接缝（Seam）**是你进行测试的公共边界：在这个接口处你观察行为而无需深入到内部。测试置于接缝处，绝不针对内部实现。

**仅在预先协商确定的接缝处进行测试。** 在编写任何测试之前，写下待测试的接缝并与用户确认。不在未确认的接缝处编写任何测试。你无法测试所有内容 — 预先对接缝达成一致是测试精力能够落脚于关键路径和复杂逻辑而非每个极端情况的关键所在。

询问："公共接口是什么？我们应该测试哪些接缝？"

## 反模式

- **实现偶合（Implementation-coupled）** — Mock 内部协同对象、测试私有方法或通过侧通道进行验证（直接查询数据库而不是使用接口）。征兆：当你进行重构但行为未改变时测试却挂掉了。
- **重言式/同义反复（Tautological）** — 断言以代码自身的方式重新计算预期值（`expect(add(a, b)).toBe(a + b)`、以相同方式手动推导出的快照、断言一个常量等于其自身），因此它凭构造就能通过，永远不可能与代码产生分歧。预期值必须来自于独立的信任源 — 明确的已知字面量、算好的实例、规范说明。
- **水平切片（Horizontal slicing）** — 先编写所有测试，然后再编写所有实现。批量编写的测试验证的是*凭空想象的*行为：你测试的是事物的*形状*而非面向用户的行为，测试对真实改变变得麻木不仁，并且你在理解实现之前就固化了测试结构。相反，应该采用**垂直切片（vertical slices）**的方式工作 — 单个测试 → 单个实现 → 循环往复，每个测试都是一枚**弹道追踪子弹（tracer bullet）**，对上一轮循环给出的反馈做出响应。

## 循环规则

- **红先于绿（Red before green）。** 先编写失败的测试，然后仅编写刚好能使其通过的代码。不要预判未来的测试，也不要添加投机性的功能。
- **一次一个切片。** 每个循环周期对应一个接缝、一个测试、一个最小实现。
- **重构不属于该循环。** 它属于评审阶段（参见 `code-review` Skill），而不属于红 → 绿的实现循环。
