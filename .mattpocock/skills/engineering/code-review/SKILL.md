基于用户提供的固定基点，从两个维度对 `HEAD` 与该基点之间的 diff 进行审查：

- **规范 (Standards)** — 代码是否符合本仓库记录的代码规范？
- **需求 (Spec)** — 代码是否忠实实现了原始 issue / PRD / 规范？

两个维度分别作为**并行子代理**运行，以避免彼此污染上下文，随后本技能会汇总它们的审查结论。

系统应当已向你提供 issue 跟踪器——如果缺少 `docs/agents/issue-tracker.md`，请运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 锚定固定基点 (Pin the fixed point)

用户指定的任何内容即为固定基点——commit SHA、分支名称、tag、`main`、`HEAD~5` 等。如果用户未指定，请主动询问。

获取一次 diff 命令：`git diff <fixed-point>...HEAD`（使用三点语法，以便针对 merge-base 进行比较）。同时通过 `git log <fixed-point>..HEAD --oneline` 记录 commit 列表。

在进一步操作之前，确认固定基点能够解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的引用或空 diff 应当在此处直接失败，而不是在两个并行子代理内部报错。

### 2. 识别需求规范来源 (Identify the spec source)

按以下顺序查找原始需求规范：

1. 提交信息中的 Issue 引用（`#123`、`Closes #45`、GitLab `!67` 等）— 通过 `docs/agents/issue-tracker.md` 中的工作流提取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的 PRD/spec 文件。
4. 如果未找到任何内容，询问用户规范保存在哪里。如果用户表示没有规范，**需求 (Spec)** 子代理将跳过并报告“无可用规范 (no spec available)”。

### 3. 识别规范标准来源 (Identify the standards sources)

仓库中记录如何编写代码的任何内容，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库自身记录的规范之外，**规范 (Standards)** 维度始终包含以下**坏味道基线 (smell baseline)**——这是一套固定的 Fowler 代码坏味道（《重构》第3章），即使仓库未提供任何文档也依然适用。受以下两条规则约束：

- **仓库规范优先。** 仓库中记录的规范始终具有最高优先级；当仓库规范认可了坏味道基线所标记的内容时，抑制该坏味道报警。
- **始终是主观裁决。** 每种坏味道都是一个带标签的启发式标准（例如“可能的依恋情结”），绝非硬性违规——并且，就像这里的任何规范一样，跳过自动化工具已强制执行的检查。

每种坏味道包含*是什么* → *如何修复*；将其与 diff 进行匹配：

- **神秘命名 (Mysterious Name)** — 函数、变量或类型的名称未能揭示其作用或包含的内容。 → 重命名；如果没有坦诚恰当的名称，说明设计本身就很模糊。
- **重复代码 (Duplicated Code)** — 相同的逻辑形状出现在变更中的多个块或文件中。 → 提取共享形状，在两处进行调用。
- **依恋情结 (Feature Envy)** — 某个方法访问另一个对象的数据比访问自身数据更频繁。 → 将该方法移动到它所依恋的数据对象上。
- **数据泥团 (Data Clumps)** — 相同的几个字段或参数总是结伴同行（预示着需要诞生一个新的类型）。 → 将它们打包为一个类型并传递。
- **基本类型偏执 (Primitive Obsession)** — 使用基本类型或字符串替代了值得拥有独立类型的领域概念。 → 为该概念赋予其独立的小型类型。
- **重复的 switch (Repeated Switches)** — 在变更中针对同一类型的相同 `switch`/`if` 级联重复出现。 → 替换为多态，或者两处共享同一个映射表。
- **发散式修改 (Shotgun Surgery / 发散修改)** — 一个逻辑变更迫使 diff 中跨多个文件进行零散修改。 → 将共同变更的内容聚合到一个模块中。
- **发散式变化 (Divergent Change)** — 出于多个不相干的原因修改同一个文件或模块。 → 拆分模块，使每个模块仅出于单一原因而改变。
- **夸夸其谈通用性 (Speculative Generality)** — 为规范中并不存在的需求添加了抽象、参数或钩子。 → 删除它；直接内联，直到出现真实需求为止。
- **消息链 (Message Chains)** — 调用者不应依赖的长 `a.b().c().d()` 导航链。 → 将遍历隐藏在第一个对象的单个方法背后。
- **中间人 (Middle Man)** — 某个类或函数大部分时间只是单纯转发调用。 → 移除它，直接调用真实目标。
- **被拒绝的遗赠 (Refused Bequest)** — 子类或实现类忽略或重写了其继承的大部分内容。 → 放弃继承，改用组合。

### 4. 并行启动两个子代理 (Spawn both sub-agents in parallel)

发送一条包含两个 `Agent` 工具调用的消息。两者都使用 `general-purpose` 子代理。

**规范标准 (Standards) 子代理提示词** — 包含：

- 完整的 diff 命令和 commit 列表。
- 你在步骤 3 中找到的标准来源文件列表，**加上步骤 3 中的坏味道基线**全文粘贴——子代理没有其他获取途径。
- 任务要求："报告（在相关的文件/块上）：(a) diff 违反已记录规范的每个位置：引用该规范（文件 + 规则）；(b) 你发现的任何基线坏味道：命名该坏味道并引用对应代码块。区分硬性违规与主观裁决——已记录规范的违反可以是硬性的，但基线坏味道始终是主观裁决，且已记录的仓库规范优先于基线。跳过自动化工具强制执行的内容。字数控制在 400 字以内。"

**需求规范 (Spec) 子代理提示词** — 包含：

- diff 命令和 commit 列表。
- 规范的路径或已获取的内容。
- 任务要求："报告：(a) 规范要求但缺失或仅部分实现的要求；(b) diff 中未被要求的行为（范围蔓延）；(c) 看起来已实现但实现方式似乎有误的要求。引用每一项发现对应的规范行。字数控制在 400 字以内。"

如果缺少规范，跳过 Spec 子代理并在最终报告中注明。

### 5. 汇总 (Aggregate)

在 `## 规范标准 (Standards)` 和 `## 需求规范 (Spec)` 标题下展示两份报告，保持原样或进行微调清理。**不要**合并或对发现结果重新排序——这两个维度故意保持独立（参见 *为什么分两个维度*）。

以单行总结结尾：每个维度的总发现数，以及*每个维度内部*最严重的问题（如果有）。不要在跨维度之间挑选单一的胜者——分离设计正是为了防止此类重新排序。

## 为什么分两个维度

一项变更可能会通过一个维度而未通过另一个维度：

- 遵循了所有规范但实现了错误功能的代码 → **规范标准通过，需求规范失败。**
- 严格按照 issue 要求实现但破坏了项目约定俗成规范的代码 → **需求规范通过，规范标准失败。**

分别汇报可以防止一个维度掩盖另一个维度。
