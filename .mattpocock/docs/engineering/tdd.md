## 它的作用

`tdd` 用于测试先行地构建功能或修复 Bug，每次处理一个具体行为，通过红绿循环驱动代码演进。

它**绝不会**预先编写所有测试。预先批量编写测试（“水平切片” horizontal slicing）产出的是对*想象中*行为的测试——它们只检查形式结构，而对真正的行为变更变得麻木。相反，`tdd` 采用垂直切片（vertical slices）：编写一个测试，然后编写刚好足以使其通过的代码，接着编写下一个测试，每个循环都基于上一个循环带给你的启发。测试仅针对公开接口，因此底层的具体实现可以自由重构而不会导致测试挂掉。

## 何时使用它

你可以输入 `/tdd`，或者当任务匹配时 AI 代理会自动调用它——测试先行地构建功能、修复 Bug，或者当你提出“红-绿-重构”（red-green-refactor）时。

当有具体行为需要构建且你希望测试能够在重构中存续时，就可以使用它。如果行为尚未确定，请先确定规范文档——对此，使用 [to-spec](https://aihero.dev/skills-to-spec)。当工作重点在于接口的形状而非测试本身时，请使用 [codebase-design](https://aihero.dev/skills-codebase-design)；`tdd` 在规划阶段会调用它来获取深层模块词汇。

## 红-绿，一次一个切片

核心理念在于**红绿循环**（red-green loop）：编写一个失败的测试（红），添加刚好足以通过它的代码（绿），然后对下一个行为重复该过程——每个循环都由上一个循环带给你的经验所启发。最开始的第一个循环是**曳光弹**（tracer bullet）：一个用来证明单条路径端到端通畅的测试，然后再以此为基础向外构建。因为你刚刚编写了代码，所以你非常清楚哪个行为至关重要以及如何去验证它——你永远不会因为贸然陷入尚未理解的测试结构中而走弯路。

两条规则保证了测试的真实可靠。好的测试读起来就像是一份规格说明（例如“用户可以使用有效的购物车进行结账”），并通过公开 API 触发真正的代码路径，因此重构内部函数名绝不会导致测试挂掉。且预期值来自于独立的唯一事实来源——已知良好的字面量、算好的示例、规范文档——而不是用代码计算的相同方式重新计算出来，后者会导致**同义反复的测试**（tautological test），即凭结构设计就必定通过却无法提供任何有效验证。

只有在测试套件处于绿色（全部通过）状态时才能进行重构；在红（失败）状态下绝不重构。

## 正常工作的标志

- 它编写一个测试，使其通过，然后才编写下一个——而不是批量写完测试然后再批量写代码。
- 测试对行为进行命名，而不是内部实现，并且能在内部重构改名后存活。
- 预期值是来自规范的字面量，而不是通过与代码完全相同的推导方式算出的数值。

## 它的位置

`tdd` 是主构建链用来编写代码的红绿循环：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[implement](https://aihero.dev/skills-implement) 是该链条中的构建步骤，它在内部驱动 `tdd` 以测试先行的方式构建每个 ticket，然后再移交给 [code-review](https://aihero.dev/skills-code-review)——因此 `tdd` 是该步骤内部的引擎，而非其本身独立的步骤。只要有具体的行为要构建而不需要完整规范时，你也可以直接调用它。它的另一个邻居是 [codebase-design](https://aihero.dev/skills-codebase-design)，它依赖后者来寻找值得在其上进行测试的深层模块接缝。当你不确定使用哪个技能或流程时，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你导航。
