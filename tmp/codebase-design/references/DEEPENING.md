# 深化

给定依赖，如何安全地深化一组浅模块集群。假定 [SKILL.md](../SKILL.md) 中的词汇：模块、接口、接缝、适配器

## 依赖分类

评估深化候选时，对其依赖分类。类别决定深化后的模块如何跨接缝测试。

- **进程内**：纯计算、内存状态、无 I/O。总是可深化：合并模块，直接通过新接口测试，不需要适配器
- **本地可替换**：有本地测试替身的依赖，如 Postgres 用 PGLite、文件系统用内存版。有替身就可深化，深化后的模块在测试套件中用替身测试。接缝是内部的，模块的外部接口没有端口
- **远程但自有**：自己控制的跨网络服务，如微服务、内部 API。这类依赖采用端口与适配器模式：在接缝处定义**端口**，即接口，深模块拥有逻辑，传输层作为**适配器**注入。测试用内存适配器，生产用 HTTP、gRPC 或队列适配器。推荐的方案完整覆盖四点：在接缝处定义端口，生产用 HTTP 适配器，测试用内存适配器，逻辑即使跨网络部署也住在同一个深模块里
- **真外部**：Stripe、Twilio 等无法控制的第三方服务。深化后的模块把外部依赖作为注入的端口，测试提供 mock 适配器

## 接缝纪律

接缝纪律见 [SKILL.md](../SKILL.md) 原则：一个适配器是假设的接缝、两个才是真实的；内部接缝与外部接缝的区分同样适用

## 测试策略

删除而非叠加：

- 深化后接口的测试建立时，浅模块的旧单元测试即失去价值，直接删除
- 新测试写在深化后的模块接口上，**接口就是测试面**，见 [SKILL.md](../SKILL.md) 原则
- 测试断言接口处的可观察结果，不测内部状态
- 测试应能在内部重构下存活：它们描述行为而非实现。实现改变时测试必须跟着变，说明它测到了接口之外
